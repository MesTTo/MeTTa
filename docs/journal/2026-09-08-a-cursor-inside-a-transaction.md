Constraint: preserve MeTTa answers, multiplicity, printed output and errors. Keep Python evaluation dispatch unchanged. Outside a transaction, preserve lazy engines and their logical update view.

Prior art: [PostgreSQL 17 DECLARE](https://www.postgresql.org/docs/17/sql-declare.html) ties a portal to its creating transaction. A `WITH HOLD` portal materializes rows and survives successful commit, while rollback removes it. This is the lifetime used here. [JDBC 21 ResultSet](https://docs.oracle.com/en/java/javase/21/docs/api/java.sql/java/sql/ResultSet.html) names hold-over-commit and close-at-commit separately; these are distinct policies, not a claim that every driver has one default. Thread-affine resources supply the other boundary: a different thread must receive an explicit refusal rather than an empty result from an invisible store.

Decided: publish `metta_host_hold/3`, `metta_host_hold_next/2`, `metta_host_hold_chunk/3` and `metta_host_hold_close/1`. The service alone chooses an engine outside a transaction or eager `findall/3` on the calling thread inside one. A held handle is `held(Id, Thread)`. Dynamic rows and their next ordinal belong to that same transaction, survive commit, and disappear on rollback. Store rows separately by cursor, owner and ordinal so pulling one does not copy the entire remaining list. A fresh atomic allocator is independent of rollback. Stepping or closing on another thread refuses with the remedy to step from the transaction's thread or open outside the transaction.

Decided: also publish `metta_host_hold_post/3`. The Node job protocol and Python's existing lazy output capture post values into suspended engines. Routing that operation through the service keeps its handle opaque; posting to an already evaluated held cursor refuses explicitly. Node start, step, resume and stop all use these services. Debugger and scheduler coroutines are interactive protocols rather than answer cursors and retain their own suspension machinery.

Decided: the shim chooses only its output transport. A captured cursor opened in a transaction uses `with_output_to/2` around one `findall/3`, then replays packets through the same hold service. The first packet carries all text, including text from an empty enumeration; later packets carry an empty string. Outside a transaction, the existing per-pull memory-stream handshake stays intact. Atomic and speculative policies and both budget builders wrap the goal before holding it. A held cursor spends its enumeration budget at open rather than across pulls; draining its rows performs no further evaluation. An Answers view still opens its underlying cursor on first demand, so that demand determines the owning transaction.

Rejected: refusing cursors inside transactions, because imports and function calls are legitimate transaction work. Revisit only if the host offers no way to enumerate on the caller.
Rejected: a Python eager branch in the evaluation dispatcher, because ownership is engine knowledge shared by every seat and belongs in the host service.
Rejected: making separate SWI engines join a transaction, because SWI's transaction stack is local virtual-machine state and supplies no joining operation.
Rejected: retracting and reasserting a whole remaining row list on every pull, because that copies a shrinking suffix repeatedly. The ordinal store preserves one evaluation and one occurrence per pull.

Closing a handle whose owner has exited is idempotent. These changes stay inside the engine service and leave Python dispatch unchanged.
