# a31.9 — stop a data payload contributing call dependencies

approach, unwanted, on i28. Refuted and kept: a31.9.1 addresses the same
issue and is built. This names the wrong walk, and the sections below are the
reasons, which is what stops it being re-entered.

## What this has to establish

A universal: for every head whose parameter carries an Atom mask, the support
graph records no call from that argument. Induction over the term walk, with
the mask as the base case. The counterexample that opened it is one case of
it, so proving the general statement and re-measuring that case settles both.

## Where the cost is

Twelve one-row files imported in sequence into `&self`, each wrapped predicate
carrying an inference-delta and call counter (`ai-tmp/probe/attrib.pl`, which
must load `engine/qlf_boot.pl` before `engine/metta.pl`; see
`ai-notes/a-probe-that-consults-metta-pl-loads-a-stale-qlf.md`).

| wrapped | import 2 | import 12 |
|---|---|---|
| `check_prolog_function_names/3` | 157 / 1 call | 157 / 1 call |
| `support_view_module/2` | 78 / 13 | 258 / 43 |
| `support_invalidate_function/1` | 403 / 1 | 483 / 1 |
| `repair_support_invalidations/0` | 1,619 / 2 | 8,769 / 2 |
| `recompile_function_in_module/2` | 1,648 / 1 | 9,018 / 1 |

One recompile per import, and logging its arguments names the same function
every time:

    2  ['$metta_exec:&self'-package-1527]
    6  ['$metta_exec:&self'-package-4255]
    12 ['$metta_exec:&self'-package-8358]

Every library's backing row is an equation on the one reserved head, so the
space holds one `package` clause per library and recompiling the head walks
all of them. The row's payload names the heads it backs, so performing it
registers those names, and the arrival of a name the equation mentions is what
schedules the recompile.

## Three designs tried on paper, two refuted

**Read the Atom mask.** `support_memo_call_head/2` refuses to descend into
`quote`, `noeval` and `Error` by a hand-written list, and `calls_head/2` in
`engine/translator/lowering.pl` says the same for the four
`prolog_function_importer/1` spellings; both exist to state what an Atom mask
states. Refuted twice over. The masked head is `perform`, and `perform` never
appears in the row, so the body the walk sees is the bare data term with no
masked head in it. And a declaration governs a name only where the module does
not define it, so a declaration on `package` would be withheld in exactly the
spaces that hold package rows, which is the wall the prelude attempt already
hit.

An Atom RESULT type does keep a body unevaluated, so the notion is real: with
`(: h (-> Atom))`, `(= (h) (g 21))` answers `(g 21)` where the undeclared and
`%Undefined%` forms both answer `(doubled 21)`. It is the declaration's reach
that blocks this route, not the notion.

**Suppress the reserved head's dependencies outright.** One clause beside the
existing list, saying a `package` equation calls nothing. Refuted by law 3,
which admits a row computed in the space under the `reads` ceiling rather than
written as a literal; a blanket rule would trade a cost now for a correctness
hole then.

**Rebuild the clause rather than the predicate.** Exactly one `package` clause
mentions the arriving head, the one the loading file just added, and
`recompile_function_in_module/2` rebuilds every clause of the head. The
support graph already records the dependency per `translated_form`, which is
per clause, and `support_translated_form_id/3` maps a form id back to its
clause reference, so the information needed to rebuild one clause is held and
then discarded. This changes no meaning, needs no declaration to reach
anywhere, and turns the per-import term from O(clauses of the head) into
O(1).

What it has to preserve: `recompile_function_in_module/2` erases and
re-appends each tracked clause in assertion order to keep their relative
order, and clauses asserted through Prolog interop are untracked and would
otherwise end up before the rebuilt ones. A per-clause rebuild must keep that
property.

## The half that is already solved

`docs/journal/2026-09-11-classes-on-metta.md`, the 2026-09-18 entry: a
definition batch entering the publication context through
`with_owning_source_load/2`, an owner PIN, had every repair filed immediate,
because `support_invalidation_action/1` skips pins when it keys a pending
repair. N definitions in one batch rebuilt each shared dependent N times. The
fix was to push the batch's load as the RUNNING load and stored owner,
`source_publication_load_context(LoadId, LoadId, Context)`, as
`with_source_load/3` pushes a file's; gated by
`filereader_source_reload:a_definition_batch_rebuilds_a_dependent_once_at_its_end`,
measured at class_decorators 13,954,646 / 19,232,576 / 13,878,634 inferences
across trunk, merge and fix.

It does not close this on its own. With one row per library the shared
dependent is rebuilt once per import either way, and what grows is the cost of
that one rebuild. It does cover a library carrying several rows, where
`package` would otherwise be rebuilt once per row, so both belong in the fix.

## The edge, read out of the graph

After three imports:

    supports(function_view('$metta_exec:&self', scale_head_2),
             translated_form('$metta_exec:&self', 10))

and `support_translated_form_id/3` maps form 10 to a clause whose head is
`'$metta_exec:&self':package(backing, _)`. So the `package` equation is
recorded as depending on every head its own payload names, and the arrival of
one is what schedules the recompile. `supports/2` holds support then derived,
which is why an earlier query in the opposite direction found nothing.
